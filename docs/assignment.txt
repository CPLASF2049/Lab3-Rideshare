一、业务功能实现
本部分规定业务功能与基本规则，接口、数据模型及服务协作方式由小组设计。相关并发、重复操作和失败恢复要求见第五部分。
1.1 身份与司机状态
支持乘客和司机登录，或选择预设账号进入系统。
司机可以开启或关闭接单。关闭接单后不再接受新订单，但仍需处理已承接的订单；订单完成或取消后，只有仍开启接单的司机才可继续接单。
后端校验操作权限：乘客只能查看和取消自己的订单，司机只能处理发给自己的派单请求和自己承接的订单。
❗允许简化：使用预设账号和简化认证，不要求注册、找回密码、实名认证和完整资料管理。
参考核心接口（仅供参考）：
接口 | 用途
POST /auth/login | 登录或选择预设身份
PUT /drivers/me/status | 设置司机上线或下线状态

1.2 选点、报价、叫车与取消
乘客通过地图或预设地点选择起终点，查看预估距离和费用。
乘客发起叫车，系统创建订单并返回受理结果，订单应关联乘客和起终点。
乘客能够查看叫车进度和接单结果。
乘客在上车前可以取消订单，包括已接单但尚未开始行程的阶段。取消后停止匹配、使该订单的派单请求失效；已有司机接单时，通知司机并解除本次订单对司机的占用。乘客可以重新叫车，行程开始后不允许普通取消。
❗允许简化：使用预设地点及简单距离、计费公式，明确标注估计值。不要求地点搜索、地址解析、真实道路距离、动态定价或取消费。
参考核心接口（仅供参考）：
接口 | 用途
POST /orders/estimate | 获取预估距离和费用
POST /orders | 创建叫车订单
GET /orders/{orderId} | 查询订单及处理进度
POST /orders/{orderId}/cancel | 上车前取消订单

1.3 派单与接单
系统为订单寻找可接单的司机并派单。可接单司机应已开启接单，且没有正在承接的订单。
司机能够查看派单信息并接受或拒绝，超过等待时间的派单请求失效。
无人可用、司机拒绝或未响应时，系统继续寻找其他司机，或结束匹配并告知乘客；匹配过程应有明确的终止条件。
同一订单只能由一名司机承接；司机从接单成功到订单完成或取消期间，不能承接其他订单。
接单成功后，乘客能够查看司机信息，司机能够查看上车点和目的地。
匹配策略、派单方式与等待时长由小组确定，不要求复杂调度算法。
参考核心接口（仅供参考）：
接口 | 用途
GET /drivers/me/offers | 查询待处理的派单
POST /offers/{offerId}/accept | 接受派单
POST /offers/{offerId}/reject | 拒绝派单

1.4 接驾、上车与结束行程
司机到达上车点后进行确认，乘客能够查看司机已到达的状态。
乘客上车后，司机确认乘客已上车并开始行程，系统记录开始时间。
到达目的地后，司机确认结束行程，系统记录结束时间、里程和费用摘要。
乘客能够查看当前和历史行程，包括起终点、司机、状态、时间及费用摘要；司机能够查看当前承接的订单及行程进度。
订单状态应能反映等待接单、已接单、司机已到达、行程中、已完成，以及取消和匹配失败等结果，具体状态模型由小组设计。
❗允许简化：到达上车点、确认乘客已上车和结束行程均通过司机按钮模拟；到达目的地可与结束行程合并。里程可使用测试数据，费用由后端规则计算，不要求连续 GPS、车辆动画或到达距离校验。
参考核心接口（仅供参考）：
接口 | 用途
POST /orders/{orderId}/arrive | 确认到达上车点
POST /orders/{orderId}/start | 确认乘客上车并开始行程
POST /orders/{orderId}/finish | 确认结束行程
GET /orders/history | 查询当前乘客的历史行程

三、CQRS 与 API 组合查询
参考第四章课件，提供独立运行的 Order（订单服务） 和 Order Query（订单查询服务），同时实现 CQRS 与 API 组合查询。
3.1 CQRS
Order 负责订单写入和业务规则校验，维护订单写模型。
Order Query 通过异步订单事件更新独立持久化的读模型，向前端提供订单详情和历史查询。
订单事件的类型、字段及同步方式由小组设计。
3.2 API 组合查询
至少选择一个订单查询场景，由 Order Query 读取自己的订单读模型，并通过 API 获取至少一个其他业务服务维护的信息，组合后返回前端。
例如，订单详情可以结合本地订单数据与其他服务提供的司机资料或车辆信息。具体查询哪些数据、调用哪些服务，由小组根据服务划分确定。
本部分在报告中说明：
订单写模型与读模型分别包含哪些数据，以及订单事件如何更新读模型。
所选组合查询需要哪些数据，由哪些服务提供，以及调用和组合过程。
重复或乱序事件、同步延迟、处理失败及查询依赖不可用等问题，按第五部分要求实现处理并说明；测试与现场验证统一见第四部分。

五、关键业务挑战与处理说明
结合本组实现，分析以下五类挑战，对实际存在的问题，应实现相应处理；因本组设计而不会出现的场景，说明原因。
5.1 并发接单与司机资源竞争
两个订单同时选择同一名司机，随后都尝试确认接单。
若同时向多名司机派单，如何处理多名司机同时接受同一订单的派单；若采用依次派单，平台向司机 A 派单，等待超时后改派给司机 B，但此时才收到 A 因网络延迟而晚到的接单请求，此时如何处理
平台向在线且空闲的司机派单后，该司机可能在接单确认前下线
说明如何保证同一订单只能由一名司机承接，以及司机在当前订单完成或取消前不能承接其他订单。明确竞争操作由哪个服务确认结果，以及未成功接单的一方得到什么反馈。
5.2 服务失败与业务恢复
根据本组服务划分，至少选择一个涉及多个服务状态变更的关键业务操作，实现失败恢复。具体参与服务、执行顺序及恢复方案由小组设计，可采用 Saga、TCC 或有明确理由的等价方案，不强制使用分布式事务框架。
考虑以下情况：
若司机占用与订单确认分属不同服务，前者已成功，但后者失败。
接单操作实际已经成功，但响应丢失，调用方只收到超时。
订单取消或结束已保存，但解除司机占用的操作尚未完成。
已向司机派单，但等待回应或处理超时期间，相关服务重启。
订单变更已保存，但事件尚未发出，或事件处理过程中服务退出。
说明以上情况系统如何处理，需要保存哪些处理进度，服务恢复后如何发现并继续未完成工作，以及恢复再次失败时如何处理。
5.3 取消、接单和开始行程之间的竞争
乘客取消订单与司机接受派单同时发生。
乘客取消订单与司机确认上车、开始行程同时发生。
说明这些操作发生竞争时，各自可能得到什么结果，以及如何保证订单状态、司机接单关系和双方看到的处理结果一致。处理结果应符合第一部分的取消规则，包括已接单但尚未开始行程时仍允许取消。
5.4 重复请求、重复事件与乱序更新
创建订单的响应丢失后重试，或乘客连续点击叫车；取消后的重新叫车应视为新操作。
司机重复接受派单、确认上车或结束行程，不能重复绑定订单、重写首次有效操作的时间或重复处理费用摘要。
Order Query 收到重复事件，或同一订单较早的状态事件晚于较新的状态事件到达。
旧订单取消并重新叫车后，针对原派单的接受请求或原订单的司机释放操作才到达，不能影响新订单。
分别说明如何处理重复请求与重复事件，如何保证去重和业务修改正确生效，以及如何避免迟到的操作或事件覆盖新状态。具体识别方式由小组设计。
5.5 订单查询延迟与组合查询失败
